## 言灵 Yanling v1.0 TODO：评论回复状态同步后端

### 背景

当前版本中，评论的「待处理」状态仅由后端初始写入 `status = "pending"` 决定，前端在用户点击「生成 AI 回复」或「回复」后**不会更新后端状态**。结果：

- 侧栏顶部的「待处理」统计只反映**最初采集时**的状态；
- 用户回复了评论后，刷新侧栏仍然显示为「待处理」；
- 多账号协同和后续报表无法区分「已跟进 / 未跟进」。

为保证体验优先，MVP 阶段采用「前端本地状态」方案：  
- 前端在本地记录哪些评论已回复，用于即时更新 UI 和统计；  
- 后端暂不感知这些状态变化。

本文档记录 v1.0 阶段需要做的「后端同步」工作，作为后续实现参考。

---

### 目标

在 v1.0 阶段完成「评论回复状态与后端同步」，实现：

- 用户**真实发送回复**后：
  - 侧栏 UI 立即把该评论从「待处理」中移除；
  - 后端对应评论记录的 `status` 更新为「已回复/已处理」；
- 所有端统一以后端状态为准：
  - 浏览器插件：跨设备/多账号视图一致；
  - 后台管理/报表：可以统计回复率、处理时长、漏斗等。

---

### 范围

- **范围内**
  - 为评论增加后端可追踪的「已回复/已处理」状态字段；
  - 新增/扩展接口，用于在用户实际回复后更新状态；
  - 前端在合适的「用户动作」节点调用该接口，并根据返回结果刷新本地状态；
  - 与现有「本地状态」方案共存（作为容错与过渡）。

- **范围外（可在后续版本考虑）**
  - 复杂的多用户权限模型（谁有权改状态）；
  - 细粒度的「处理中 / 暂缓 / 忽略」等多状态；
  - 与三方 CRM / 工单系统的深度集成。

---

### 后端设计草案

#### 1. 数据库层

- 在 `comments` 表中增加/统一状态字段（如已存在可复用）：
  - `status`：`'pending' | 'replied' | 'ignored' | ...'`
  - 或增加单独布尔字段：`is_replied`（需要与现有 `status` 字段协调）。
- 为状态字段建立必要索引，便于统计和筛选：
  - 如：`idx_comments_status_intent_level`。

#### 2. API 设计

- 新增或扩展接口（示意）：

  - `POST /api/comments/:id/mark-replied`
    - 请求体（可选）：`{ replyChannel: "xiaohongshu", repliedAt?: ISODateString }`
    - 行为：
      - 校验 `tenantId` / `userId` 是否有权限；
      - 将 `status` 更新为 `'replied'`（或 `is_replied = true`）；
      - 记录 `replied_at` 时间戳（若表中存在相应字段）；
      - 返回更新后的评论摘要。

  - 或在现有 `PATCH /api/comments/:id` 基础上增加 `status` 更新能力。

#### 3. 业务规则

- 仅在「用户真实发送回复」后更新状态：
  - 不是点击「生成 AI 回复」，而是确认填入并发送（或你认为足够接近「已处理」的动作）。
- 同一条评论多次更新：
  - 再次调用 `mark-replied` 应为幂等操作；
  - 可以记录最近一次 `replied_at`，但不应反向改回 `pending`。

---

### 前端方案（与本地状态共存）

#### 1. 当前行为回顾

- 本地已/未回复目前仅通过前端计划中的「本地状态」判断：
  - 如：使用 `@plasmohq/storage` 维护 `localRepliedIds: Set<platformCommentId>`；
  - 顶部「待处理」统计和筛选逻辑读的是「合并后的状态」。

#### 2. v1.0 行为升级

- 点击「回复」（并确认已发送）时：
  1. 立即更新本地状态（保证 UI 与统计即时反馈）；
  2. 同时调用后端 `mark-replied` 接口：
     - 成功：无需额外处理，本地状态与后端已一致；
     - 失败：可选择：
       - 仅在控制台记录错误，不打扰用户；
       - 或在下次拉取评论时尝试重试。

- 拉取评论时合并逻辑：
  - 以**后端状态为主**，本地状态为辅：
    - 若后端已是 `'replied'`，则无论本地是否记录，视为已回复；
    - 若后端还是 `'pending'`，但本地标记为已回复，可视为「待同步」状态：
      - 短期内（如几分钟内）继续沿用本地视图；
      - 定期/下次成功调用时清除本地 pending 标记。

---

### 交互与文案建议

- 在 UI 上区分：
  - 「待处理」：后端 `status = 'pending'` 且本地未标记回复；
  - 「已回复」：后端 `status = 'replied'` 或本地标记已回复；
- 可能的视觉表现：
  - 已回复评论整体卡片略淡、按钮变为「已回复」或「重新回复」；
  - 「待处理」筛选仅展示 `pending` 状态的评论。

---

### 实施顺序建议

1. 先在前端完成「本地已回复状态」逻辑（当前阶段）。  
2. v1.0 时：
   - 增加/迁移数据库字段与后端接口；
   - 在 `background` / `sidepanel` 中接入 `mark-replied` 调用；
   - 调整「合并状态」策略，以后端为主、本地为辅。
